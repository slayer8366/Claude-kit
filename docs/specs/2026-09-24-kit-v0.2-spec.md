# Claude-kit v0.2 specification

Status: approved by the owner 2026-09-24 (scope, planner tools, order). Base: main at aeb4d0b.
Sources: RECORD.md entries 2026-09-23-04 (R6), 2026-09-23-07 (deferred list), and the kit v0.1 fixes intent (owner ruling items).

## Goal
Stop the stops. The v0.1 fixes needed six re-sent dispatches. The causes were four gaps: dispatches saved in scattered places under colliding names, sessions running stale hooks, a planner that cannot reach a running coder, and no clean way to resume a lost session. v0.2 closes those, then the earlier ruling items.

## Decisions (owner, 2026-09-24)
- The planner role gains SendMessage, sending a prompt to a named agent unchanged, and TaskStop.
- All four phases are in v0.2.
- Order: Step 0, then phases 1, 2, 3, 4. Phase 1 comes before phase 3 because the naming rule shapes the recording tool and the resume helper.

## Step 0: housekeeping (no code)
- Move ~/Zynergy/Claude-kit from kit-v0.1 to main.
- Confirm new harness worktrees start from main; the five existing ones sit at 9390407 with v0.1 hooks.
- Settle the untracked 2026-09-23-05.md and -06.md in that checkout; their copies are recorded on main.

## Phase 1: dispatch storage and naming
1. One naming rule for saved dispatches, the same in every worktree (R6(a), extended by the UTC-date naming and by per-worktree numbering colliding).
2. A written rule for the store names of dispatches saved outside the store.
3. A recording tool that finds hook-saved dispatches across all harness worktrees, hashes them, and produces the copies and citations.
4. Record format: a dispatch-note outcome `stopped`; an entry kind for continuing an intent (R6(b)); a fixed order for a dispatch's own copy against its notes.

## Phase 2: session integrity
5. A session-start check that warns when the session's checkout or hooks differ from what is expected.
6. Resuming after a disconnect: a written procedure, and a helper that reads the lost session's log and lists what was sent and what came back.
7. A session launcher with a time limit, a check for the expected session, and cleanup on failure.
8. A live-exercise runner that drives the exercise cases and collects the log lines as evidence.

## Phase 3: planner-to-agent communication
9. The planner may use SendMessage (R6(c)), so a ruling reaches a running or stopped coder without a full re-send.
10. The planner may send a prompt to a named agent unchanged.
11. The planner may use TaskStop.

## Phase 4: ruling items and smaller fixes
12. history_guard over-blocking on unparseable push commands.
13. Upgrades removing dropped files.
14. A kit bypass table.
15. Backups: "created after" means file birth time, written down.
16. Blocked Agent calls are logged with `toolDenialKind`, not a `deny` decision (Claude Code behaviour): document it and match on that field in evidence checks.

## Owner additions
17. A coder may merge a pull request when the dispatch's `Merge` section reads `authorised`, and only after writing a backup that lets the owner undo the merge: a git bundle of the base branch, `merge.json` and `MANIFEST.sha256` in a new folder under the kit.json key `backup_dir`, named in that directory's `INDEX.md`. history_guard checks the backup, the caller's role and the command's form (a merge commit or a squash) before it lets the merge through (owner, 2026-09-25).
