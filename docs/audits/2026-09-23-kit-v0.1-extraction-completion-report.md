## Decisions I made

1. **Step 1 as a verbatim import.** I read "skeleton" as importing the 16 source files unchanged, so that each later step's diff shows exactly what the port changed. The alternative was empty placeholders. Deciding it properly needed the planner's intent for "skeleton".
2. **The saved dispatch** is a byte-identical copy of Forager's `prompts/preserved/2026-09-23-03.md`, including its hook header (Forager HEAD, target, timestamp), stored as `prompts/preserved/2026-09-23-01.md`. I did not copy the first run's prompt (`2026-09-23-02.md`) into the kit store. The sweep was vacuous.
3. **JSON key names:** `android_package`, `protected_branches`, `dispatchable_agents`, `type_targets`, `required_sections`, `checkers_dir`, `guard_env_prefix`.
4. **Validation strictness.** None of these limits were given in the dispatch:
   - `protected_branches` and `dispatchable_agents` must be non-empty;
   - every `type_targets` agent must be dispatchable;
   - `type_targets` and `required_sections` must name the same types;
   - `checkers_dir` must be relative, with no `..`;
   - the prefix must match `[A-Z_][A-Z0-9_]*`;
   - the package is any non-empty string without whitespace, with no Java-syntax check.
5. **Config error behaviour.** The config is loaded before the payload is read. A problem produces a deny naming the hook's script file and every problem found.
6. **Test harness.** Every hook test runs a temporary copy of the hooks with a test config beside it. The alternative was a config-path override in the hooks, which would have been a new input to a guard. The test config reproduces the source's values, with fake identifiers.
7. **Test placement.**
   - The config tests are a new file, `test_config.py`.
   - The config-value tests are in the existing per-guard files.
   - They landed in step 3 with the hooks change, not in step 4, so that they could fail against the hard-coded hooks first.
8. **Message wording.** The dispatch asked for the change but not the words:
   - "from the device" replaces "from the owner's phone";
   - history messages name the branch;
   - approval messages name the rule;
   - the no-Type message lists the configured types;
   - docstrings keep Claude Code version facts (2.1.280, 2.1.63) without dates or step numbers.
9. **Kept literal and flagged rather than generalised:** the approval split on `build`/`device`, the "pulse dispatch" allow message, and the role names.
10. **Agent wording:**
    - `CLAUDE.md` is read "if the repository has one";
    - the section list points at `required_sections`;
    - the checkers point at `checkers_dir`;
    - the pulse's foreground rule points at `android_package`, "when one is named".
11. **`release.json`** is the one release-set definition: its name, its format (JSON), its location at the root, and its split into vendored files and templates.
12. **install.py behaviour beyond the rulings:**
    - it accepts `refs/tags` only;
    - it reads every file from the tag, not the working tree;
    - it checks everything before writing anything;
    - it overwrites existing vendored files other than `settings.json`;
    - the lock holds the tag and the hashes only;
    - the checkers are installed at the root whatever `checkers_dir` says;
    - it refuses a release set that would vendor an adopter-owned path.
13. **check_kit.py:** a missing or unreadable lock fails, and a missing vendored file fails with its name.
14. **tests/ and the adopter integration test.** The install and release tests live in `tests/`. One of them runs the vendored hook tests inside the installed adopter.
15. **Denylist format and patterns.** One regex per line. Some patterns are broad: `/home/[a-z]`, any e-mail outside the example domains, and any 16-digit hex. `release_check.py` fails closed on a missing or empty denylist or a missing release file, and it scans the template sources too. The patterns avoid writing the owner's e-mail address into the repository.
16. **behaviour_diff.py** lives in `workshop/`. It derives the source config from b2435ef's hook constants rather than holding Forager values itself.
17. **CI:**
    - ubuntu-24.04 for both versions;
    - Python `3.8` and `3.14`;

    - triggered on push and pull_request.
18. **File names:**

## Flags outside scope

1. **A Type added in config runs without approval.** The approval split is hard-coded to the Type names `build` and `device` (`dispatch_guard.py`, `if type_ in ("build", "device")`). Any other Type an adopter adds to `type_targets` is allowed without approval, and its message says "pulse dispatch". This is a fail-open that config alone can reach. It needs its own dispatch, with a design decision on where approval is configured.
2. **Dispatch-notes only accept three Types.** `check_record.py`'s `NOTE_TYPES` is `{"build", "device", "pulse"}`, so a dispatch-note for a configured Type outside that set is invalid.
3. **A renamed pulse agent is unrestricted.** `role_guard.py` restricts the literal role name `pulse`. An adopter that names its read-only agent something else in `dispatchable_agents` gets no role_guard restriction on it.
4. **A non-default `checkers_dir` is not coherent end to end.** The hook finds `check_prompts.py` there, but:
   - the checkers look for `RECORD.md` and `prompts/` beside themselves;
   - the hook writes to `<root>/prompts/preserved`;
   - `install.py` installs the checkers at the root;
   - `test_dispatch_guard.py` copies them from the root.

   `test_checker_location_comes_from_config` shows the symptom: exit 1, because there is no `RECORD.md` beside the relocated checkers. The owner ruled that the checker paths do not change.
5. **Grep and Glob remain where the owner ruled they stay.** They are in the pulse allowlist (`role_guard.py`) and in both agents' `tools:` lines, and they are inert on 2.1.280.
6. **install.py does not prune.** A file vendored by an earlier tag and dropped by a later release stays in the adopter. No upgrade from one tag to another was tested.
7. **history_guard denies harmless commands that mention "push".** It denies any Bash command that contains the word `push` and does not parse, for example a heredoc commit message with an apostrophe. This happened twice in this session, under Forager's copy of the hook, which is the same code. Forager's device_guard also blocked one command whose heredoc merely contained the gradle task name. Nothing ran in any of those cases. I worked around them by writing messages and patches to files, not by bypassing the guards.
8. **The kit has no record of the guards' known bypasses.** The ported docstrings no longer point at Forager's bypass table, and the kit has none of its own.
9. **The upstream checker docstrings mention files adopters do not have.** They cite EGD's own record entries and `DURABILITY.md`, and are kept as upstream text.
10. **The kit's name will become public.** Released files, and therefore public adopters, will carry the name "Claude-kit" and cite "Claude-kit RECORD.md 2026-09-23-01", a private record. The dispatch asked for the checker attribution. The owner should confirm the name is fit to publish.
11. **Forager's untracked prompts are still waiting.** `prompts/preserved/2026-09-23-01.md` to `-03.md` remain untracked in the Forager worktree, deferred by ruling 4.
12. **Scratch files remain in `/tmp`, none deleted:**
    - `/tmp/kitsrc-b2435ef`, `/tmp/egd-35e39d1`, `/tmp/kit_denylist_probe`;
    - `/tmp/kit_saved`, `/tmp/kit_evidence`;
    - `/tmp/kit_patch_*.py`, `/tmp/kit_msg_*.txt`, `/tmp/kit_py_manifest.json`, `/tmp/kit_pr_body.md`.

    The first run's `/tmp/kitsrc`, `/tmp/egd` and `/tmp/kit_pulse.txt` are untouched.
